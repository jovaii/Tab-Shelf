# App Store and GitHub Release Design

## Status

The product and commercial direction was approved by James Li on 24 August 2026. This written specification is ready for final review before implementation planning.

## Goal

Prepare Tab Shelf for public discovery and trustworthy distribution through two complementary channels without weakening its privacy promise or creating separate product editions:

1. The complete source remains publicly available on GitHub under Apache License 2.0 for free inspection and self-building.
2. The Mac App Store offers the same core product for a one-time price of USD 9.99, providing Apple-reviewed installation, signing, automatic updates, and a convenient supported release.

Success means a Safari user can understand the product, its privacy model, and the two installation choices before downloading it. The paid edition sells convenience and supported distribution, not exclusive functionality.

## Product and Commercial Model

Tab Shelf remains a Safari-only macOS utility under the Jovaii brand, created by James Li. There is one product, one feature set, and one source tree.

The GitHub repository provides source code, development documentation, screenshots, and self-build instructions. It does not publish an unsigned or ad-hoc App binary as a consumer download. Source archives generated by GitHub remain available.

The Mac App Store edition is priced at USD 9.99 as a one-time upfront purchase. It contains no advertising, subscription, in-app purchase, license server, account system, feature lock, telemetry, or external payment link. Apple handles purchase entitlement and distribution, so Tab Shelf does not implement its own customer or payment database.

The public comparison language is:

| Channel | Price | Included value |
| --- | --- | --- |
| Build from source | Free | Complete Apache-2.0 source and local build workflow |
| Mac App Store | USD 9.99 one time | The same core features with Apple-reviewed installation, signing, automatic updates, and supported releases |

## Distribution Architecture

The existing Safari Web Extension remains the single product core. It is embedded in the native macOS host App and uses the existing identifiers:

- Host App: `com.jovaii.tabshelf`
- Safari extension: `com.jovaii.tabshelf.extension`

Development and App Store builds use the same versioned extension resources. Build configuration, signing identity, provisioning, and packaging may differ, but product behavior must not drift between channels.

The current generated Xcode project already enables App Sandbox and automatic signing for both targets. Implementation will verify and formalize these settings rather than assume that generated defaults are sufficient. Distribution certificates, provisioning profiles, Apple credentials, API keys, and private keys must remain in Xcode, Keychain, or Apple systems and must never be committed.

GitHub development builds keep the existing local preview, test, audit, packaging, and installation workflows. App Store delivery receives a separate validation and archive path that cannot accidentally ad-hoc sign or package a public consumer binary.

## Native Host App

The native host App becomes a clear, polished entry point rather than a technical container. Its primary screen includes:

- Tab Shelf identity, short value proposition, and current version.
- A concise three-step Safari enablement guide.
- A button that opens Safari extension settings.
- A visible status explanation for enabled, disabled, or unavailable extension states when the platform API exposes that state.
- Links to privacy, support, source code, and license information.
- A short statement that tab and theme data stay on the current Mac.

The host App does not duplicate the shelf, theme editor, or tab-management interface. Those remain inside Safari, where the functionality belongs. The host must use system-native controls, support light and dark appearance, remain usable with VoiceOver and keyboard navigation, and avoid remote web content.

## Privacy and Permissions

The existing privacy contract remains binding:

- No telemetry, analytics, advertising, tracking, account data, or first-party network request.
- Only Safari `tabs` and `storage` extension permissions.
- Preferences and optional personal background images remain in Safari local extension storage.
- No remote fonts, remote artwork, analytics SDK, ad SDK, or payment SDK.

App Store privacy answers may state that no data is collected only after the final packaged binary, dependencies, and network behavior have been verified. Store copy must explain why browsing-history access appears in Safari: the extension reads the user's open tabs locally so it can group and manage them. Permission copy must not imply collection or transmission.

## GitHub Discovery Experience

The repository becomes the canonical public product and developer page. All public-facing content remains English-only and uses only the Tab Shelf, James Li, and Jovaii identities.

The upgraded repository presentation includes:

- A visual README hero showing the real shelf interface.
- A short product promise above the fold.
- A compact feature overview, privacy summary, and Safari-only compatibility statement.
- A screenshot gallery covering the shelf, card accents, Theme Studio, and native host App.
- Clearly separated **Build from source — Free** and **Mac App Store — USD 9.99 one time** paths.
- A Mac App Store badge only after the public store URL exists.
- Build, test, support, privacy, license, and contribution information.
- GitHub topics, social-preview artwork, repository description, and homepage/support links.

No star target, artificial engagement tactic, paid review, or forced GitHub prompt is introduced. Discovery relies on an understandable listing, searchable metadata, useful visuals, release notes, and organic sharing.

## App Store Connect Delivery

The App Store submission requires an active Apple Developer Program membership and completion of Apple's paid-app agreements, tax information, and banking setup. The implementation package will prepare, but cannot fabricate or bypass, account-owned information.

The delivery set includes:

- App record, name, subtitle, description, keywords, category, copyright, support URL, privacy URL, and source/product URL.
- App privacy answers supported by the verified binary.
- Age-rating answers appropriate for a tab utility with no accounts, social features, advertising, or user-generated content service.
- Required Mac screenshots captured from the real signed candidate.
- App icon and store artwork derived from the existing original Tab Shelf identity.
- Version and build numbers that match the archived targets and extension manifest.
- Review notes explaining Safari extension enablement, local tab access, new-tab replacement, and how the reviewer can exercise the product.

The first release is submitted through Xcode Organizer using Apple Distribution and App Store provisioning. Direct Developer ID distribution and notarized downloads are outside this release because the Mac App Store is the chosen paid channel.

## Build, Validation, and Release Flow

Implementation will add an App Store readiness command that fails early when repository-controlled requirements are incomplete. It verifies at least:

- Product names, bundle identifiers, versions, and build numbers agree.
- App Sandbox remains enabled for the host and extension targets.
- Required entitlements are minimal and expected.
- The packaged App includes `LICENSE`, `NOTICE`, and `THIRD_PARTY_NOTICES.md`.
- No secrets, signing exports, prohibited legacy names, remote runtime assets, ad code, analytics code, or unexpected network permissions appear.
- Release resources contain the current tested extension files.

The release sequence is:

1. Run dependency-free unit tests and the repository audit.
2. Render and inspect the existing desktop and compact WebKit acceptance views.
3. Build the native host and verify the extension appears exactly once in Safari.
4. Exercise first-run guidance, extension enablement, new-tab replacement, tab activation and closing, duplicate cleanup, theme selection, image background handling, export/import, keyboard navigation, and reduced motion.
5. Archive the App Store configuration in Xcode with the enrolled Apple team.
6. Validate the archive before upload.
7. Upload the candidate, complete App Store Connect metadata, and submit it for review.
8. Add the public store link and badge to GitHub only after Apple publishes the listing.

Tests that mutate or close Safari tabs must use disposable tabs. A failed validation, signing, upload, or review step stops the release and records the exact error; scripts must not replace certificates, delete user data, broaden entitlements, or weaken security settings to force success.

## Documentation and Support

Public documentation stays in the repository and can be exposed through GitHub Pages where a stable HTTPS URL is required. It includes:

- User-facing privacy policy.
- Support and troubleshooting page.
- Source-build and development instructions.
- App Store installation and Safari enablement instructions.
- Release notes and known limitations.

Support initially uses GitHub Issues with templates for bugs and feature requests. Reports must warn users not to include private browsing history, private URLs, credentials, or personal screenshots.

## Scope and Non-Goals

This release includes GitHub presentation, App Store readiness, native onboarding, store metadata, signing/archive guidance, QA, and submission support.

It explicitly excludes:

- Advertising or an ad-supported free binary.
- Subscriptions, trials, in-app purchases, donations, or external checkout.
- Accounts, cloud sync, analytics, telemetry, crash-reporting SDKs, or license servers.
- Chrome, Chromium, Firefox, iOS, or visionOS support.
- A separate premium feature branch.
- Direct Developer ID distribution or a public GitHub App binary.
- Marketing promises that cannot be demonstrated by the shipping build.

## Estimated Effort and Efficiency

The engineering and release-preparation estimate is 16–28 working hours, excluding Apple identity verification, contract processing, bank/tax verification, and App Review waiting time:

| Workstream | Estimate |
| --- | ---: |
| GitHub presentation, policy pages, and store copy | 3–5 hours |
| Native host onboarding and accessibility | 4–6 hours |
| App Store build validation, signing, and metadata setup | 4–7 hours |
| Visual QA, packaged-App QA, archive, and submission | 5–10 hours |

The largest costs are native-host polish, signed-build verification, store screenshots, and end-to-end Safari QA. Reusing the existing extension, bundle identifiers, Sandbox-enabled Xcode project, dependency-free tests, preview renderer, icons, and packaging checks avoids a rewrite. Excluding ads, accounts, in-app purchases, and a license backend removes the highest-risk commercial infrastructure and keeps the plan within approximately two to four focused working days.

## Acceptance Criteria

- GitHub presents Tab Shelf as a polished English-only Safari product with accurate privacy, feature, build, and commercial information.
- Public source remains complete and Apache-2.0 licensed; no public consumer App binary is attached to GitHub releases.
- The Mac App Store candidate offers the same core features for USD 9.99 once, with no ads, subscription, account, telemetry, or license server.
- The native host provides understandable Safari setup, support, privacy, version, and extension-status guidance.
- Host and extension identifiers remain `com.jovaii.tabshelf` and `com.jovaii.tabshelf.extension`.
- App Sandbox, minimal permissions, legal files, version alignment, independence audit, automated tests, visual QA, and single-extension registration all pass.
- Secrets and Apple account material remain outside Git and distributable artifacts.
- App Store metadata and privacy answers match the verified candidate.
- The public store badge is added only after a real Apple listing URL exists.
- Any external-account blocker is reported precisely without weakening product security or inventing completion.
